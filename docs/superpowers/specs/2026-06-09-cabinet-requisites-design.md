# Реквизиты юр.лица в личном кабинете — дизайн

Дата: 2026-06-09
Проект: СплитХаб (splithub.ru)

## Цель

Дать залогиненному клиенту возможность самостоятельно ввести и в дальнейшем
**редактировать** реквизиты юридического лица в личном кабинете, чтобы эти данные
собирались в профиль и попадали в Excel-экспорт «Клиенты».

## Контекст

- Регистрация на сайте простая: имя, телефон, Telegram, пароль (`api/auth.php?action=register`).
  Юр.данные при регистрации НЕ собираются — это сохраняется.
- Личный кабинет — модалка `dash-modal` в `index.html`, содержимое рисует `renderDashTab(tab)`.
  Сейчас две вкладки: «Заказы» и «Профиль».
- `api/auth.php?action=profile` возвращает `id, name, phone, telegram, role, created_at` и баланс
  бонусов. Действия для сохранения профиля/реквизитов НЕТ.
- Колонки `company_name, inn, kpp, legal_address` в таблице `users` уже есть (миграция в
  `db/init.php` добавлена ранее).
- Excel-экспорт «Клиенты» (`api/admin.php?action=export_xlsx`) уже читает эти 4 колонки —
  как только клиент их заполнит, графы в выгрузке наполнятся. Экспорт менять не нужно.
- Брошенная B2B-фича в админке (`edit_user`) не используется и вне рамок этой задачи.

## Решения (зафиксированы с заказчиком)

- **Набор полей:** минимум — Наименование организации, ИНН, КПП, Юридический адрес.
- **Размещение:** отдельная вкладка «Реквизиты» в кабинете (рядом с «Заказы»/«Профиль»).
- **В уведомление о заказе НЕ добавляем** — только хранение в профиле + Excel.
- **Редактирование обязательно:** форма всегда доступна для правки, значения предзагружаются,
  повторное сохранение перезаписывает. Никакой блокировки после первого сохранения.

## Архитектура

### 1. Бэкенд — `api/auth.php`

**a) Расширить действие `profile`:** в SELECT добавить `company_name, inn, kpp, legal_address`
(через `COALESCE(...,'')`), чтобы фронт подставлял текущие значения в форму при каждом открытии.

**b) Новое действие `update_requisites` (POST):**
- Под `authRequire()` — гость получает 401.
- Тело JSON: `{ company_name, inn, kpp, legal_address }`.
- Валидация (только при непустом значении):
  - `inn` — только цифры, длина 10 (юр.лицо) или 12 (ИП); иначе 422.
  - `kpp` — только цифры, длина 9; иначе 422.
  - `company_name` — trim, обрезка до 255 символов.
  - `legal_address` — trim, обрезка до 500 символов.
  - Пустые значения разрешены (физлицо/очистка поля).
- `UPDATE users SET company_name=?, inn=?, kpp=?, legal_address=? WHERE id = <текущий uid>`
  (параметризовано).
- Ответ: `{ ok:true, requisites:{...сохранённые значения...} }`.

### 2. Фронтенд — `index.html` (кабинет)

**a)** В `renderDashTab` добавить третью вкладку «Реквизиты» в строку `dash-tabs`.

**b)** Ветка `tab === 'requisites'`: рисует форму из 4 полей, **предзаполненную** значениями из
`currentUser` (которые приходят из `profile`):
- Наименование организации (на всю ширину)
- ИНН и КПП (в ряд)
- Юридический адрес (на всю ширину)
- Кнопка «Сохранить реквизиты»
- Подсказка сверху: «Заполните, если вы юридическое лицо — реквизиты сохранятся в вашем
  профиле для выставления счетов. Физлицам заполнять не нужно.»
- Значения экранируются при подстановке в `value` (защита от поломки разметки).

**c)** Функция `saveRequisites()`:
- Считывает 4 поля, POST `api/auth.php?action=update_requisites`.
- На `ok`: обновляет поля в `currentUser`, показывает подтверждение «✓ Реквизиты сохранены».
- На ошибку (422/сеть): тост с текстом ошибки, значения формы сохраняются (не сбрасываются).

### Редактируемость (ключевое требование)

- Вкладку можно открывать сколько угодно раз; форма каждый раз показывает **актуальные
  сохранённые** значения (из `profile`/`currentUser`).
- Любое поле можно изменить или очистить и сохранить заново — `update_requisites` всегда
  перезаписывает (идемпотентный UPDATE). Кнопка всегда «Сохранить», состояния «только чтение» нет.

## Поток данных

Клиент логинится → открывает ЛК → вкладка «Реквизиты» (поля предзаполнены) → правит → «Сохранить»
→ `update_requisites` пишет в `users` → при следующем открытии значения снова подгружаются →
админ видит их в Excel-экспорте «Клиенты».

## Обработка ошибок

- `update_requisites` без сессии → 401; невалидные ИНН/КПП → 422 без записи.
- Сетевые/серверные сбои не сбрасывают введённые значения в форме.
- Все запросы параметризованы (как принято в проекте).

## Затрагиваемые файлы

- `api/auth.php` — расширить `profile`, добавить `update_requisites`.
- `index.html` — вкладка «Реквизиты», форма, `saveRequisites()`.
- Не трогаем: `db/init.php` (колонки уже есть), `api/admin.php` (экспорт уже читает поля),
  `send.php`, `admin.html`.

## Критерии готовности (проверяемые)

1. У залогиненного клиента в ЛК есть вкладка «Реквизиты» с 4 полями.
2. Сохранение пишет значения в `users`; `profile` их возвращает; при повторном открытии вкладки
   поля предзаполнены сохранённым.
3. Повторное редактирование перезаписывает значения; очистка поля сохраняет пустое.
4. Неверный ИНН (не 10/12 цифр) или КПП (не 9 цифр) → ответ 422, запись не меняется.
5. Гость (без сессии) получает 401 на `update_requisites`.
6. Заполненные реквизиты появляются в Excel-экспорте «Клиенты».

## Вне рамок (YAGNI)

- Банковские реквизиты (р/с, БИК, банк, к/с), ОГРН — выбран минимальный набор.
- Реквизиты в уведомлении о заказе (TG/email) — заказчик отклонил.
- Починка админского `edit_user` — отдельная задача.
- Несколько компаний на одного пользователя — одна запись реквизитов на пользователя.
